When people talk about AI agents, they often ask how far the system can act on its own. Working on an on-duty workflow led me to a different question: what does an agent pass on when it stops?

An agent that investigates and leaves behind a pile of logs and an unexplained decision makes the next person start over. The hand-off matters as much as the investigation.

## We did not start with an autonomous platform

On duty, you need to find useful data, understand what changed, check the repository and runbook, then decide what to do. Context is scattered across dashboards, tickets, and earlier investigations. It is an investigation under time pressure.

The person on duty asks questions such as:

- Is this a real incident or a noisy signal?
- Which system is actually responsible?
- What changed recently?
- What evidence would distinguish the likely causes?
- Is the safest next step a rollback, a patch, a configuration change, or more observation?

The first steps often repeat: compare current and expected state, look for recent changes, run known diagnostics. We assigned those steps to small, specialized agents.

## Small agents, close to the work

One agent collects evidence, another knows the relevant codebase, and a third tests a hypothesis or prepares a patch. The person on duty spends less time gathering context and more time interpreting the results.

> We did not automate responsibility. We automated investigation.

The human still owns the decision. They choose which agent to call, in what order, and when there is enough evidence. Agents inspect, compare, and propose; their output alone does not authorise a risky change.

## What happens when the agents call one another?

Once those agents exist, it is tempting to chain them: collect data, inspect the repository, prepare a patch, validate it. But the human was doing more than launching the next step.

They weighed evidence, noticed contradictions, abandoned disproven hypotheses, and decided when another opinion was needed. If agents call one another, that orchestration must become explicit.

An orchestrator may continue a well-supported, low-risk task or request a review. To choose, it needs the investigation state, not just the last answer:

- What was the objective, and which paths have been ruled out?
- What evidence supports the current hypothesis, and what is missing?
- What has already been tried?
- How confident are we, and what are the risks of the next actions?

Without that, the chain moves forward while losing the thread.

## Context is necessary, but it is not enough

Finding the right documents and granting the right tools is necessary. So is passing on the reasoning built from them.

A hand-off should not merely say:

```text
The error rate increased at 14:03.
```

That is an isolated fact. Here is a hand-off the next person can use:

```text
Investigation: elevated error rate in the checkout service

Current assessment: likely regression in the payment retry path
Confidence: medium

Evidence:
- Errors began shortly after the latest checkout deployment.
- The increase is concentrated in retry-related requests.
- The dependent payment provider does not show a corresponding increase.

Ruled out:
- A broad provider outage
- A database saturation event

Not yet checked:
- Whether the new retry configuration is active in every region

Recommended next actions:
1. Compare the active configuration across regions.
2. If the configuration is inconsistent, pause rollout and prepare a rollback.
3. Escalate before changing production configuration.
```

It shows the hypothesis, the evidence, the discarded paths, and what remains uncertain. The next agent—or the human—can continue without starting over.

## A place to take over

An event could trigger an automatic investigation, after which the orchestrator posts a structured hand-off in a Slack thread. The person on duty would see the evidence, hypotheses, confidence, and possible actions at the moment their judgment is needed.

The same format could live in a ticket, pull request, or incident timeline. Between agents, too, a compact state is more useful than a raw transcript that each recipient must reinterpret.

## Designing a good hand-off protocol

A hand-off should make six things explicit:

1. **The original objective**, so the chain does not drift.
2. **The current hypothesis** and confidence level.
3. **The evidence and its provenance**, so others can check it.
4. **The paths ruled out**, so they are not repeated.
5. **The next step**: investigate, review, approve, or escalate.
6. **The cost of being wrong**, which determines whether a person must decide.

Confidence alone is not enough. A low-risk diagnostic can run automatically; a production change may need review even when the hypothesis looks strong.

Approving every tiny step recreates the bottleneck. Continuing without checkpoints can make errors costly. The system can run bounded diagnostics, then pause before an ambiguous or high-impact action. The person gets enough context to challenge the reasoning, choose an option, and add what the agents could not know.

## Better hand-offs are a form of system reliability

The reliability of an agent workflow also depends on what the next participant understands. Can they tell observation from hypothesis, check the evidence, and know whether a recommendation is ready to execute or only worth investigating?

Evaluation should examine that hand-off, not just each agent's answer. An unfinished investigation still helps if it narrows the possibilities and shows what remains uncertain.

Real work brings ambiguity, changing constraints, and decisions with unequal consequences. An agent needs to know when to proceed and when to ask for judgment. Our on-duty workflow showed that it must also preserve the investigation as work changes hands.

The question is simple: when the agent stops, does the next person know what to check and which decision to make?
