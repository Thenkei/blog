Notre manière de travailler a beaucoup changé ces derniers mois. Chez **RockFi**, on écrit moins de code à la main et on passe davantage de temps à cadrer les demandes et à vérifier les changements proposés par les agents.

## Décembre : on quitte Cursor pour Claude Code

<ArticleDiagram visualId="engineering-2026-ai-redefined-our-job" />

Fin 2025, vers décembre, l'équipe tech (10 à 12 personnes à ce moment-là) est passée de Cursor à **Claude Code**. Nous voulions un agent capable de travailler dans le terminal et dans le repo, avec les contraintes du projet, plutôt que de compléter nos lignes de code.

Personne n'a eu besoin d'imposer la migration : les gens ont essayé l'outil sur leurs tâches, puis ont changé d'eux-mêmes.

Je peux lui confier une partie de l'implémentation avec les fichiers et les conventions du repo. Je dois ensuite vérifier comment il les a interprétés, notamment lorsqu'un changement touche plusieurs services.

## Les outils maison pour les tâches répétitives

Nous avons construit des outils autour de Claude Code pour les tâches qui revenaient souvent :

- **Workshops et brainstorming** : rassembler le contexte utile et structurer la discussion.
- **Préparation des DiveIn** : reprendre les décisions et les questions ouvertes dans notre template de conception.
- **Préparation des PR** : créer la branche, récupérer le contexte, préparer la description et lier les documents.

Ces outils nous évitent une partie du travail répétitif. Il reste à vérifier que le document reprend correctement la décision et que la PR correspond au besoin.

## Pourquoi je garde Codex et Claude Code

En plus de la stack commune à l'équipe, j'utilise **Codex** et **Claude Code** en parallèle.

J'utilise surtout Codex pour des modifications ciblées, avec des allers-retours courts. Claude Code, c'est plutôt celui que j'ouvre pour discuter d'une décision d'architecture ou déboguer un problème distribué qui demande de garder beaucoup de contexte. C'est ma répartition des tâches à ce moment-là, pas une limite de ce que chaque outil sait faire.

Avec ce duo, je travaille sur **4 à 5 projets par jour**. Une régression d'observabilité à corriger dans un repo, une migration de base de données à relire dans un autre, et mon projet principal qui avance au milieu de tout ça.

Je ne suis pas devenu multitâche pour autant, mon cerveau reste mono-thread. L'outil garde le fil de chaque repo, ce qui m'aide à reprendre un sujet laissé deux heures plus tôt. Le context switching reste là ; j'ai moins de contexte à reconstruire à chaque fois.

## Le temps passé en review

La génération d'une première version prend moins de temps. La review en prend toujours : vérifier un comportement métier, comprendre une migration, examiner les accès à la base. Nous faisions déjà ce travail avant l'IA. Il devient plus difficile de le suivre quand les diffs arrivent plus vite.

Des skills de code review dans Claude Code et Codex font une première passe. Ils peuvent signaler un problème ou proposer une vérification supplémentaire. Il faut ensuite examiner ces remarques et le diff, avec les contraintes du système en tête.

## Le contexte à fournir

L'agent doit savoir quelles conventions s'appliquent, quels contrats préserver et quelles parties du système sont concernées. Dans un repo ancien, il peut trouver plusieurs patterns et suivre celui que nous n'utilisons plus.

Choisir les fichiers et les décisions à lui donner fait donc partie du travail. Le résultat peut être cohérent avec le contexte fourni et incompatible avec une contrainte oubliée.

## Une dépendance supplémentaire aux API

Une indisponibilité d'Anthropic ou d'OpenAI ralentirait les tâches que nous avons pris l'habitude de déléguer. C'est une dépendance supplémentaire dans notre workflow. Il faut pouvoir reprendre ces tâches sans l'agent, même si cela prend plus de temps.
