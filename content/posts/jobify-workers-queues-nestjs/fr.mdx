Si vous utilisez déjà `@nestjs/bullmq`, félicitations, vous avez survécu au premier boss. Vous pouvez garder exactement la même stack et obtenir des contrats de jobs beaucoup plus stricts. L'idée : arrêter de réécrire du boilerplate et ajouter une fine couche `jobify` qui standardise l'enqueue, l'enregistrement des processors, les timeouts, les retries, le tracing et l'exécution séquentielle. Fini les jobs morts en silence à 4 h du matin.

## Intégration NestJS classique (point de départ)

<ArticleDiagram visualId="jobify-workers-queues-nestjs" />

```typescript
@Injectable()
export class ExportsService {
  constructor(@InjectQueue("exports") private readonly queue: Queue) {}

  async enqueueExport(payload: ExportPayload) {
    return this.queue.add("activity-export", payload, {
      priority: 2,
      removeOnComplete: true,
      removeOnFail: true,
    });
  }
}
```

Ça fonctionne. C'est le « Hello World » des queues. Mais à mesure que le nombre de jobs augmente, on se retrouve vite avec un plat de spaghettis : des options de queue dupliquées, un typage très faible entre producer et consumer, et des comportements improvisés pour l'idempotence, le debounce et l'exécution séquentielle. Chaque nouveau job copie les options du précédent, erreurs comprises.

## Ce que la couche Jobify apporte

Le pattern `make-jobify.ts` crée un contrat unique : **on enregistre une fois côté workers, on appelle un runner typé partout ailleurs.**

- **Fonction nommée obligatoire :** une fonction anonyme est refusée, pour garder des clés de processor stables.
- **Enregistrement côté worker uniquement :** les processors ne sont ajoutés que si `isWorker` vaut `true` et qu'ils ne sont pas déjà présents.
- **Priorité dynamique :** la priorité peut être une valeur statique, une fonction synchrone ou une fonction asynchrone.
- **Contrat de debounce :** `delayInMs`, `makeJobId` et `name` sont obligatoires, avec des vérifications de marqueurs pour éviter les erreurs de configuration.

```typescript
const runExport = jobify(exportApprovals, {
  priority: JobPriority.low,
  timeoutInMinutes: 180,
  onError: onExportError,
  makeJobId: (params) =>
    "approvals-" + params.environmentId + "-" + params.from + "-" + params.to,
});

await runExport({ userId, projectId, environmentId, from, to });
```

## Comportement de queue centralisé au même endroit

Dans `queue-service.ts`, le comportement d'enqueue est explicite et réutilisable :

- **propagation de trace :** les paramètres de span sont embarqués à la création du job ;
- **reschedule du debounce :** les jobs delayed sont retrouvés par `jobId` et replanifiés sur place avec `changeDelay` ;
- **sécurité des repeatables :** les anciennes configurations repeatable sont supprimées pour éviter les doubles schedules après un redéploiement ;
- **hygiène de queue :** `removeOnComplete` et `removeOnFail` sont activés par défaut pour éviter que le stockage ne dérive.

## Exécution worker enveloppée dans un ordre fixe

`worker-service.ts` applique les wrappers dans un ordre strict : monitoring -> onError -> timeout -> work.

```typescript
const timeoutWrap = timeoutAfterMinutes(
  jobFunction,
  timeoutInMinutes || DEFAULT_TIMEOUT,
);
const onErrorWrap = WorkerService.onErrorWrap(job, timeoutWrap, options);
const monitoringWrap = workerMonitoringService.monitoringWrap({
  name,
  job,
  work: onErrorWrap,
  service: options.service,
});

await monitoringWrap();
```

Résultat : la même sémantique de timeout, des hooks d'erreur prévisibles et des labels de monitoring uniformes, sans que chaque équipe réécrive la même plomberie.

## Exécution séquentielle avec make-jobify-sequential

`make-jobify-sequential.ts` répond à un problème classique des systèmes distribués : certaines actions doivent être sérialisées pour une même entité logique, tout en restant concurrentes entre entités différentes.

- **Modèle de clés :** `sequentialKey` définit la lane, `processingKey` identifie le type d'action et `identifier` restreint le scope à une entité.
- **File dans une liste Redis :** les arguments sont ajoutés avec `RPUSH` et consommés avec `LRANGE/LPOP`.
- **Sécurité :** le dépilement se fait dans le `finally`, pour qu'un processor en échec ne bloque pas la lane indéfiniment.
- **Chaînage :** `onComplete` déclenche le traitement suivant en attente pour la même lane et le même identifiant.

```typescript
const registerSequential = makeJobifySequential({
  jobify,
  jobsRedisClient,
  logger,
  datadogService,
});

const runSyncUser = registerSequential({
  sequentialKey: "user-sync",
  processingKey: "sync-profile",
  getSequentialId: (userId) => String(userId),
  priority: JobPriority.normal,
  processor: async (userId) => {
    await syncUserProfile(userId);
  },
});
```

## Cas concret d'export : les approbations d'actions

`action-approvals-exporter.ts` montre le chemin complet : lancement en queue, export en streaming, lien signé (TTL de 24 h) et notification de l'utilisateur.

- mise en queue avec `JobPriority.low` et un timeout explicite lu dans l'environnement ;
- tracing désactivé pour ces exports lourds et longs ;
- pipeline de streams : `Readable.from(iterator) -> Transform -> csv-stringify -> S3 multipart writable` ;
- les e-mails de succès et d'échec sont branchés directement via `onError` et la logique de complétion.

## Cas d'orchestration cloud complexe : l'agent hébergé de Forest Admin

Pour notre version Cloud entièrement hébergée, nous reposons sur des jobs lourdement orchestrés pour éviter que l'API principale ne s'effondre. Lorsqu'un utilisateur modifie son schéma ou supprime un environnement, nous lançons des jobs asynchrones qui gèrent des démontages d'infrastructure complexes ou de la synchronisation de données à travers des milliers de projets.

- **Synchronisation avec debounce :** lorsqu'une API Map change, nous appliquons un debounce au job de redéploiement (`debouncedSynchronizeAgentData`), parce que les utilisateurs sauvegardent souvent en rafale. Nous ne voulons pas 10 redéploiements Lambda simultanés pour un seul environnement.
- **Suppression en file d'attente :** supprimer un environnement cloud implique d'effacer des objets S3, de démonter les configurations de NAT Gateway et de mettre à jour notre Postgres central. On envoie tout cela dans un job `cloudDeleteService.queuedDeleteAgent()`. Si AWS nous applique une limite de débit, BullMQ retente la suppression plus tard, sans laisser d'infrastructure fantôme traîner (ni payer la taxe NAT pour rien).
- **Priorité des jobs :** nous routons strictement ces événements d'orchestration : une synchronisation visible par l'utilisateur passe avant un job de nettoyage de fond.

## Ce que NestJS gagne à ce pattern

Gardez les décorateurs et les modules Nest. Ajoutez un petit package interne qui expose des adaptateurs `jobify`, `queueService` et `workerService`, et optionnellement `jobifySequential`.

```typescript
@Injectable()
export class JobifyFactory {
  constructor(
    private readonly queueService: QueueService,
    private readonly workerService: WorkerService,
    @Inject(IS_WORKER) private readonly isWorker: boolean,
  ) {}

  create<T extends (...args: any[]) => Promise<any>>(
    work: T,
    options: JobOptions<T>,
  ) {
    return makeJobify({
      queueService: this.queueService,
      workerService: this.workerService,
      isWorker: this.isWorker,
      logConfig: (k, v) => logger.info({ key: k, value: v }),
      assertPresent,
    })(work, options);
  }
}
```

## Stratégie de migration sans interruption de service

1. Envelopper un export lourd existant avec jobify.
2. Déplacer les options de queue des callsites vers les valeurs par défaut de `JobOptions`.
3. Ajouter un `makeJobId` déterministe pour l'idempotence et le debounce.
4. N'introduire des lanes séquentielles que là où l'ordre d'écriture est une exigence stricte.
5. Déployer des dashboards (profondeur de queue, jobs actifs, échecs, percentiles de durée p95/p99) avant de généraliser.

## Règles de design

- **Ne pas exposer les objets `Job` de BullMQ** au code métier par défaut : passez plutôt des arguments typés. Sinon, votre logique métier se retrouve couplée aux entrailles de BullMQ, et vous pleurerez à la prochaine montée de version majeure.
- **Toujours imposer des timeouts par défaut** : le comportement au shutdown dépend d'une exécution de job bornée.
- **Garder les contrats producer et consumer au même endroit** (l'appel à jobify), plutôt qu'éparpillés entre modules.
- **Traiter les lanes séquentielles comme une ressource rare** : ne les utiliser que là où la correction exige la sérialisation.

Ce que cette approche apporte, c'est du déterminisme opérationnel : quand un job échoue à 4 h du matin, il échoue comme tous les autres, avec le même timeout, le même hook d'erreur et les mêmes labels de monitoring.
