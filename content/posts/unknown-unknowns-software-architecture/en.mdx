## Context

Architecture reviews handle risks a team can name: expected load, provider availability, migration consistency, and retry strategy. The real danger sits outside that list: a shared but unwritten assumption, an interaction missing from the diagram, or a failure mode nobody has encountered yet.

These are **unknown unknowns**. Thariq Shihipar's [A Field Guide to Fable: Finding Your Unknowns](https://x.com/trq212/article/2073100352921215386) describes the gap between the *map* supplied to an agent and the real *territory*. The same gap exists in software design: production includes operators, time, historical data, providers, and usage patterns that the document does not represent.

## The problem

A design can satisfy every written scenario and fail on an interaction outside the model: a request retried while the first attempt is still running, an event received after its target was deleted, or a provider returning a technically valid but operationally incomplete response.

The test suite did not lie. We asked it yesterday's questions. The more convincing the document or AI answer looks, the more dangerous that appearance of completeness becomes.

## Bad ideas

The first bad idea is pursuing an exhaustive diagram. More boxes do not model time, concurrency, or degraded modes.

The second is treating a checklist as proof. A checklist covers known risks; it does not automatically reveal an assumption missing from everyone's model.

The third is asking an agent to “find every risk”. It can widen the inspected surface and challenge reasoning, but it can only discover what leaves evidence in sources it may access.

## What did not work

We tried reviews centred on the nominal path: who calls whom, which component owns the data, and which API exposes the contract. They produced clean documents but postponed the important questions: what happens when the call is duplicated, reordered, partially applied, or replayed by an operator?

Generic questions also produced generic answers. “Will it scale?” opens few useful paths. “Which cardinality assumption breaks this component first?” demands evidence.

## Alternatives

We now use an internal review tool before consequential decisions. It orchestrates three separate moves: **gates** check known invariants, a **find blind spots** pass searches code, documents, and history for unproven assumptions, and **adversarial reviews** attack the proposal across operations, security, data, product, and deployment boundaries.

The tool does not decide. It produces traceable questions, connects each one to evidence or missing evidence, and asks explicitly:

- which financial or domain invariant could fail silently;
- which dependency shares our blast radius;
- which manual operation bypasses the nominal path;
- which signal would expose the issue before a customer does;
- which recovery remains possible when the assumption is false.

A human reviewer remains accountable and may accept a bounded risk.

## The solution

We no longer try to predict every failure. We make surprises observable and recoverable:

1. **Reduce** assumptions through explicit contracts and executable invariants.
2. **Isolate** components and permissions to contain the blast radius.
3. **Detect** divergence through metrics, traces, reconciliation, and domain alerts.
4. **Recover** through idempotency, controlled replay, kill switches, rollback, or compensation.

The exit question is simple: if this assumption becomes false tomorrow, will we see it, limit the impact, and return to a safe state?

## Limits

This method does not turn the unknown into the known. It can create noise, reward excessive caution, and delay reversible decisions. Effort must remain proportional to blast radius: more evidence for a financial calculation or irreversible migration, less for an isolated experiment that is easy to undo.

An adversarial review can also inherit the blind spots of its sources. Incidents, operator feedback, and production evidence remain irreplaceable. The goal is not certainty; it is bounded, observable, owned uncertainty.
