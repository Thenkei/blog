## The diagram stops at production

Architecture reviews are good at discussing risks a team can name: expected load, provider availability, migration consistency, retry strategy. A document can cover all four and still leave its most important assumption in the margins.

That assumption may be shared but unwritten. It may be an interaction missing from the diagram, or a failure mode nobody in the room has encountered yet. These are the **unknown unknowns**: not the risks we forgot to tick off, but the ones that never made it onto the list.

Thariq Shihipar's [A Field Guide to Fable: Finding Your Unknowns](https://x.com/trq212/article/2073100352921215386) describes the gap between the *map* supplied to an agent and the real *territory*. Software has the same gap. Production contains operators, time, historical data, providers, and usage patterns that the design document cannot fully represent.

## Production always brings a plus-one

A design can satisfy every written scenario and still fail on an interaction outside the model. A request is retried while the first attempt is still running. An event arrives after its target has been deleted. A provider returns a response that is technically valid and operationally incomplete.

The test suite did not lie; we asked it yesterday's questions. The danger is the comfortable leap from “everything we tested passed” to “we have modelled everything that matters”. A polished design document—or an AI answer delivered with perfect confidence—can make that leap especially easy to miss.

## Three comfortable stories

**The exhaustive diagram.** Add enough boxes and every risk will eventually appear. Except boxes are poor at representing time, concurrency, manual intervention, and degraded modes.

**The checklist as proof.** A checklist is useful precisely because it remembers known risks. It does not reveal an assumption that is absent from everyone's model.

**The omniscient agent.** Asking an agent to “find every risk” can widen the inspected surface and challenge a line of reasoning. It still discovers only what leaves evidence in sources the agent can access.

None of these tools is useless. The mistake is asking any of them to certify completeness.

## Ask questions with teeth

Nominal-path reviews tend to produce clean documents: who calls whom, which component owns the data, which API exposes the contract. They also postpone the awkward questions. What happens when the call is duplicated, reordered, partially applied, or replayed by an operator?

The wording matters. “Will it scale?” invites a generic answer. “Which cardinality assumption breaks this component first?” sends the reviewer looking for evidence.

Before consequential decisions, we use an internal review tool to bring several kinds of scrutiny into the same room. **Gates** check known invariants. A **find blind spots** pass searches code, documents, and history for unproven assumptions. **Adversarial reviews** attack the proposal across operations, security, data, product, and deployment boundaries.

The tool does not decide. It produces traceable questions, connects each one to evidence—or to the conspicuous absence of evidence—and asks:

- Which financial or domain invariant could fail silently?
- Which dependency shares our blast radius?
- Which manual operation bypasses the nominal path?
- Which signal would expose the issue before a customer does?
- Which recovery path remains possible when the assumption is false?

A human reviewer remains accountable. Accepting a bounded risk is a decision; overlooking it is not.

## Build the fire exits while it is still quiet

The practical goal is not to predict every failure. It is to make the eventual surprise visible, contain its impact, and keep the system recoverable:

1. **Reduce** assumptions through explicit contracts and executable invariants.
2. **Isolate** components and permissions to contain the blast radius.
3. **Detect** divergence through metrics, traces, reconciliation, and domain alerts.
4. **Recover** through idempotency, controlled replay, kill switches, rollback, or compensation.

This leaves one useful exit question: if the assumption becomes false tomorrow, will we see it, limit the impact, and return to a safe state?

## The map stays unfinished

No review method turns the unknown into the known. This one can create noise, reward excessive caution, and delay decisions that would have been cheap to reverse. The effort should follow the blast radius: demand more evidence for a financial calculation or an irreversible migration than for an isolated experiment with an obvious undo button.

Adversarial reviews can also inherit the blind spots of their sources. Incidents, operator feedback, and production evidence remain irreplaceable. The point is not certainty. It is uncertainty that is bounded, observable, and owned.
