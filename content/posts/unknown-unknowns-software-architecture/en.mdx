## What an architecture review does not see

Architecture reviews handle known risks well: load, availability, migrations, retries. A review can cover all four and still miss the assumption that matters most, because nobody wrote it down.

These are the **unknown unknowns**: an assumption that stayed implicit, or a failure mode that is missing from the diagram. They never made it onto the list of risks.

Thariq Shihipar's [A Field Guide to Fable: Finding Your Unknowns](https://x.com/trq212/article/2073100352921215386) describes the gap between the description given to an agent and the real system. The same applies to software: no document fully represents operators, historical data, and production usage.

## What the tests do not cover

A design can pass every written scenario and still fail when a request is retried while the first attempt is still running, or when an event arrives after its target has been deleted.

Both have happened to us. So have others: a system that changed between the spec and the implementation, latency in a distributed system that nobody had thought about, and business rules nobody had specified, which we only learned about after the release.

The tests are not wrong. They answer the questions we thought to ask. “All tests passed” does not mean “we modelled everything”.

## What is not enough

The first reflex is to add detail to the diagram. More boxes do little to show time, concurrency, or manual intervention. A checklist records the risks we already know, so it cannot contain an assumption nobody has thought of.

An agent does not solve this either. It can inspect more sources than we can, but it only finds what left a trace in them. None of these tools can certify that a review is complete.

## Questions that ask for evidence

A review that follows the nominal path describes the components. It does not say what happens when a call is duplicated, reordered, or replayed by an operator.

“Will it scale?” gets a generic answer. “Which cardinality assumption breaks this component first?” makes the reviewer look for evidence.

Before an important decision, our internal tool combines **gates** for known invariants, a **find blind spots** pass for unproven assumptions, and **adversarial reviews** across operations, security, data, and deployment.

It has already happened several times: the blind-spots pass brought up an assumption that nobody had written down and that the usual review had missed.

The tool links each question to evidence, or shows that the evidence is missing:

- Which financial or domain invariant could fail silently?
- Which dependency would also be affected by our failure?
- Which manual operation bypasses the nominal path?
- Which signal would expose the issue before a customer does?
- Which action is still possible when the assumption is false?

The decision stays with a human. To accept a risk, you first have to have identified it.

## Prepare the recovery before the incident

We will not predict every failure. We can make a surprise visible, limit its impact, and get back to a safe state.

It starts with fewer implicit assumptions: explicit contracts and executable invariants. Isolating components and permissions then limits the blast radius. To detect divergence, we rely on metrics, traces, reconciliation, and domain alerts. Then comes the way back: idempotency, controlled replay, kill switches, rollback, or compensation. These have to be in place before the incident.

For each assumption that remains, we ask: if it becomes false tomorrow, will we notice and respond?

## Limits of the method

This method can create noise and slow down decisions that are easy to undo. The effort should match the possible consequences: a financial calculation or an irreversible migration needs more evidence than an isolated experiment.

Reviews also inherit the blind spots of their sources. Incidents, operator feedback, and production data remain irreplaceable. What we want to know is what is still uncertain and how we will monitor it.
