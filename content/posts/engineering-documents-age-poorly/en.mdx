An engineering document can become wrong without changing a single word.

An architecture decision or runbook may be accurate when published. Then the code changes, a provider updates its contract, or production reveals an exception. The page still looks authoritative.

An AI assistant may even retrieve it, treat it as reliable context, and turn it into a plan or code.

## The page that still looks employed

Most wikis know who created a page and when it was edited. Few say what evidence supports it, which change should trigger a review, or what replaced it.

A missing page announces its absence. A stale one still looks like an active reference, even when its assumptions belong to history.

“Last updated Tuesday” does not rescue the reader. It proves that someone touched the page on Tuesday, not that anyone verified the contract it describes.

## What does not fix it

- Review every page quarterly, regardless of what changed.
- Generate documentation from code and assume it also captures domain decisions.
- Keep archives among active references.
- Confuse “last updated” with “last verified”.
- Assign documentation to everyone without naming an owner for each page.

A clean-up campaign brings temporary relief. Then commits, migrations, and incidents make some pages wrong again. AI makes writing cheaper, not verification; it may even smooth over contradictory sources. Maintenance needs to follow the changes that affect what the page describes.

## Documents have different half-lives

There is no reason to maintain every category in the same way:

- an **ADR** is immutable; a new ADR supersedes it;
- a **runbook** has to be exercised against real operations;
- an **API reference** can be generated from an executable contract;
- a **DiveIn** preserves the original decision and links to amendments;
- an **exploration note** may expire without ever being updated.

Each kind of document needs its own rule for review or expiry.

## Six questions before a page can claim authority

Before an active document asks anyone to trust it, it should answer six questions:

| Field | Purpose |
| --- | --- |
| Status | Draft, active, superseded, or archived |
| Owner | Person or team accountable for validity |
| Evidence | Code, schema, test, metric, or decision supporting it |
| Trigger | Event requiring review |
| Expiry | Date or condition after which it is no longer authoritative |
| Successor | Document replacing this version |

These fields help readers spot when a page may no longer be authoritative.

## Review the page where reality changed

A pull request that changes a contract can list affected documents. A migration may invalidate a runbook; an incident may correct a procedure. Review happens while the evidence is still at hand.

AI can find affected pages and prepare a diff. The owner checks the meaning before publishing.

## There is no immortality clause

These fields cannot guarantee a review: some dependencies between code and prose remain hard to detect. Focus this effort on pages that guide decisions or repeated actions. Historical notes can stay as they are when their status is clear.

The goal is simple: an old page should no longer pass for today's reference.
