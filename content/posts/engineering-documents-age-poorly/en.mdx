An engineering document can become wrong without changing a single word.

An architecture decision or runbook may be accurate when published. Then the code changes, a provider updates its contract, or production reveals an exception. The page still looks authoritative.

An AI assistant may even retrieve it, treat it as reliable context, and turn it into a plan or code.

## The outdated page that still looks authoritative

Most wikis know who created a page and when it was edited. Few say what evidence supports it, which change should trigger a review, or what replaced it.

When a page is missing, you notice. An outdated page still looks like an active reference, even when the assumptions behind it are no longer true.

It has happened to us with three kinds of pages: a runbook that no longer matched what was running, a design decision that had been replaced without the page saying so, and a DiveIn that the delivered behaviour had moved away from.

“Last updated Tuesday” does not help much. It says that someone edited the page on Tuesday. It does not say that anyone checked what the page describes.

## What is not enough

- Review every page quarterly, regardless of what changed.
- Generate documentation from code and assume it also captures domain decisions.
- Keep archives among active references.
- Confuse “last updated” with “last verified”.
- Assign documentation to everyone without naming an owner for each page.

A big clean-up helps for a while. Then commits, migrations, and incidents make some pages wrong again. AI makes pages faster to write, but it does not make them faster to check, and it can smooth over sources that contradict each other. Reviews have to be tied to the changes that affect what the page describes.

## Not all documents age the same way

There is no reason to maintain every category in the same way:

- an **ADR** is immutable; a new ADR supersedes it;
- a **runbook** has to be exercised against real operations;
- an **API reference** can be generated from an executable contract;
- a **DiveIn** preserves the original decision and links to amendments;
- an **exploration note** may expire without ever being updated.

Each kind of document needs its own rule for review or expiry.

## Six questions before trusting a page

Before anyone relies on an active document, it should answer six questions:

| Field | Purpose |
| --- | --- |
| Status | Draft, active, superseded, or archived |
| Owner | Person or team accountable for validity |
| Evidence | Code, schema, test, metric, or decision supporting it |
| Trigger | Event requiring review |
| Expiry | Date or condition after which it is no longer authoritative |
| Successor | Document replacing this version |

These fields tell the reader when the page needs to be checked again before relying on it.

## Review the page when something changes

A pull request that changes a contract can list the affected documents. A migration may invalidate a runbook; an incident may correct a procedure. The page is then reviewed while the evidence is still available.

AI can find affected pages and prepare a diff. The owner checks the meaning before publishing.

## Someone still has to do the review

We do not have these fields everywhere. Today only some kinds of documents carry them, and most pages do not.

These fields do not guarantee that a review happens: some dependencies between code and prose remain hard to detect. I would spend this effort on the pages that guide decisions or repeated actions. A historical note can stay as it is when its status is clear.

An old page should no longer be mistaken for the current reference.
