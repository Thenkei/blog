## Context

An architecture decision, runbook, or DiveIn is accurate when the team writes it. Then code changes, a provider modifies its contract, ownership moves, and production exposes an exception. The document remains in place with the same appearance of authority.

AI assistants raise the stakes: a stale page is no longer read only by a cautious person. It can be retrieved automatically and turned into a plan or code.

## The problem

Most wikis optimise creation rather than lifecycle. They record who created a page but rarely which evidence makes it true, which change should trigger review, or when it should stop guiding a decision.

The result is not missing documentation. It is worse: current decisions, historical assumptions, and partially correct tutorials all presented with the same confidence.

## Bad ideas

- Review every page quarterly without connecting reviews to real changes.
- Generate more documentation from code and assume it stays correct.
- Keep every document for history without distinguishing archive from active reference.
- Treat “last updated” as sufficient evidence of trust.
- Make documentation the diffuse responsibility of the whole team.

A recent date proves nothing unless somebody verified the described contract.

## What did not work

Clean-up campaigns improved the wiki for weeks, then drift resumed. They were disconnected from commits, migrations, incidents, and ownership changes that made pages false.

AI generation reduced writing cost but not validation cost. It sometimes created more convincing prose from contradictory sources. Generating a document establishes neither truth nor validity duration.

Long “everything” pages failed too: each section aged at a different rate and had no precise owner.

## Alternatives

Documents need different maintenance models:

- an **ADR** is immutable; a new ADR supersedes it;
- a **runbook** must be exercised against real operations;
- an **API reference** can be generated from an executable contract;
- a **DiveIn** preserves the original decision and links to amendments;
- an **exploration note** may expire without being updated.

The alternative to maintaining everything is not deleting everything. It is assigning an explicit lifecycle to each category.

## The solution

An active document carries a minimum contract:

| Field | Purpose |
| --- | --- |
| Status | Draft, active, superseded, or archived |
| Owner | Person or team accountable for validity |
| Evidence | Code, schema, test, metric, or decision supporting it |
| Trigger | Event requiring review |
| Expiry | Date or condition after which it is no longer authoritative |
| Successor | Document replacing this version |

Documentation review belongs in the change workflow: a PR modifying a contract lists dependent documents; a migration invalidates the old runbook; an incident creates or corrects the missing procedure. AI may locate candidate references and prepare a diff. The owner confirms meaning and publishes.

## Limits

This contract adds metadata and cannot guarantee that an owner will act. Dependencies between code and prose remain hard to detect exhaustively. A page may be correct but useless, or become obsolete without an identifiable technical change.

Apply this maintenance level to documents that guide decisions or repeated actions. Historical notes may remain frozen when their status is clear. The goal is not a perfectly fresh wiki; it is the absence of misleading authority.
