Second episode of **What Trustworthy Data Costs**. The first was about getting data into the warehouse. This one is about getting it back out, which is far less documented and far more dangerous.

The scenario is simple. An advisor opens a screen. On it is a number computed in the warehouse: a consolidation, an indicator, cleaned-up partner data. They use it to talk to a client.

We use this path for analytical results served back to applications, including client portfolio performance and market opportunities matched with advisors’ clients. A late or inconsistent value is therefore a product issue, not just a warehouse issue.

The first question is: **as of when?**

## The freshness budget (do the math)

Nobody decides that data will be two hours old. It happens by addition.

Take a typical chain, with intervals that are each reasonable on their own (illustrative example, not our configuration):

| Step | Trigger | Worst case added |
| --- | --- | --- |
| Source extraction | every hour | 60 min + sync duration |
| dbt transformation | every hour, independent clock | 60 min + run duration |
| Reverse sync to the application | every 15 min | 15 min + apply duration |

Add the three maximum waits: **two hours and fifteen minutes**, before execution time, retries and queueing. That is an upper bound for these intervals, not a measured percentile. The actual delay depends on the clocks’ relative phases. Scheduled jobs do not become real time because someone puts “near” in front of it.

Two waits are avoidable: transformation can follow a completed extraction, and publication can follow a validated transformation.

## Chain on events, not on clocks

Dagster can trigger Airbyte syncs and track dependencies as assets. Our configuration combines scheduled dbt SLA tiers with reactive chains; not every model is event-driven. For a reactive publication step, this example illustrates the condition rather than reproducing our implementation:

```python
from dagster import AssetExecutionContext, AssetKey, AutomationCondition, asset

@asset(
    deps=[AssetKey(["gold", "account_metrics"])],
    # Request publication after an update, subject to blocking checks.
    automation_condition=(
        AutomationCondition.eager()
        & AutomationCondition.all_deps_blocking_checks_passed()
    ),
    group_name="reverse_etl",
)
def account_metrics_projection(context: AssetExecutionContext, projection_store: ProjectionStore) -> None:
    run = projection_store.publish_from_warehouse(
        dataset="account_metrics",
        dagster_run_id=context.run_id,
    )
    context.add_output_metadata({"rows": run.row_count, "as_of": run.as_of.isoformat()})
```

For that chain, the planned waits shrink to the extraction interval. Durations, sensor evaluation, queueing and retries still count. The automation sensor must be enabled. `ProjectionStore` represents application-specific code supplied as a Dagster resource; it is not a library API.

There is still a floor: the source itself. If a partner publishes once a day, no orchestration will make its data hourly. **The freshness budget is negotiated with the business, source by source**, and it gets written down somewhere.

## Two systems, two truths

The application has its own database, and its users write to it. The warehouse has a copy, which is older. Reverse ETL sends back values computed from that copy.

Consider this failure:

1. At 10:00, extraction reads the old value.
2. At 10:02, a user edits the field in the application.
3. At 10:40, reverse ETL sends back a row computed from the old value, and writes it into the same table.
4. The 10:02 edit is gone. No error, no log. The user swears they saved. They are right.

Reverse ETL just performed **last-writer-wins with stale data**.

The rule that removes this whole class of bugs: **a field has exactly one owner**. Either the application writes it, or the warehouse computes it. Never both.

One way to enforce that ownership is a dedicated projection schema: the publication process writes it, the application reads it and joins it to its own data. Sharing a table is possible with strict column privileges, but a schema boundary is easier to inspect. The examples below describe this publication pattern; they are not extracts from our deployed reverse ETL.

## Apply, don't overwrite

Even in a dedicated schema, a run can arrive late, be replayed, or overlap with the next one. Every write must therefore be **conditional and idempotent**.

For an incremental sync, the guard fits in one clause:

```sql
insert into projection.account_metrics as current
    (account_id, metric_value, computed_as_of, run_id)
values ($1, $2, $3, $4)
on conflict (account_id) do update
    set metric_value   = excluded.metric_value,
        computed_as_of = excluded.computed_as_of,
        run_id         = excluded.run_id
    -- This WHERE is the whole post: a replayed or late run
    -- can no longer overwrite a fresher value.
    where current.computed_as_of < excluded.computed_as_of;
```

This requires non-null ordering timestamps with a defined meaning: source coverage, not the time the worker finished. A timestamp tie is a no-op only if the payload is the same. Conflicting payloads need a source revision or an error; arrival order cannot settle it. An incremental projection also needs explicit tombstones for deletions.

For a full snapshot, **the application must never see a half-written run**. If half the rows are from 10:00 and half from 11:00, the totals match no real state. Write and validate an immutable run first, then publish its pointer:

```sql
-- Publication, once every row of the run has been inserted.
update projection.current_run
   set run_id = $1, as_of = $2
 where dataset = 'account_metrics'
   and as_of < $2; -- An old run that finishes last does not win.

-- Application read: a complete run, or nothing.
select m.metric_value, r.as_of
  from projection.account_metrics_runs m
  join projection.current_run r
    on r.dataset = 'account_metrics' and m.run_id = r.run_id
 where m.account_id = $1;
```

The pointer row must already exist, and the referenced run must be fully committed before this update. Check the affected-row count: zero means the run was not published. Readers join through the pointer in one statement; cleanup must retain the current run and any rollback candidate. A rollback is a separate, audited operation: this forward-only update deliberately refuses an older timestamp. Only a validated, complete snapshot can make absence mean deletion. A truncated extraction must not publish.

## Show the time

Once you accept that data has an age, you have to **show it**. In our line of work, a number without an "as of" is not information, it is a liability.

Each projection needs a defined `as_of` and an explicit freshness budget. If a result combines several sources, record their coverage separately; the freshest timestamp must not hide an older dependency. For one coverage timestamp, a small pure function can classify the display state:

```ts
export type Freshness = "fresh" | "stale" | "expired" | "unknown";

export type FreshnessBudget = {
  staleAfterMs: number;
  expireAfterMs: number;
  maxFutureSkewMs: number;
};

export function freshnessOf(asOf: Date, now: Date, budget: FreshnessBudget): Freshness {
  const { staleAfterMs, expireAfterMs, maxFutureSkewMs } = budget;
  const ageMs = now.getTime() - asOf.getTime();
  if (
    ![ageMs, staleAfterMs, expireAfterMs, maxFutureSkewMs].every(Number.isFinite)
    || staleAfterMs < 0
    || expireAfterMs <= staleAfterMs
    || maxFutureSkewMs < 0
    || ageMs < -maxFutureSkewMs
  ) return "unknown";

  if (ageMs >= expireAfterMs) return "expired";
  if (ageMs >= staleAfterMs) return "stale";
  return "fresh";
}
```

`unknown` covers invalid dates, inconsistent budgets and timestamps too far in the future. The caller should record that anomaly and show an unavailable state. `expired` does the same for known data that is too old. Use timezone-qualified timestamps; do not reset `as_of` to the publication time, which would make old source data look new.

## Why serve from an operational store?

Direct warehouse reads can work for analytical screens. For an operational screen, they add dependencies that need to fit the product's latency and availability budgets:

- **Latency.** Queueing, query startup and warehouse resume time count as well as SQL execution. Benchmark the actual lookup under load; the database category alone does not settle it.
- **Cost.** Frequent queries can keep a warehouse active instead of letting it suspend. Compare that cost with maintaining the projection.
- **Availability.** The application inherits every maintenance window, upgrade, and incident of the data platform. The blast radius of a broken dbt model now includes your product.

The warehouse computes. **An operational store serves.** Reverse ETL is exactly the bridge between the two, which is why it deserves this much care.

## The operating cost of another pipeline

- **One more pipeline to operate.** Reverse ETL has its own failures, its own replays, its own alerts. It does not just inherit those of the previous steps: it adds them up.
- **Freshness is monitored end to end.** One alert per step does not tell you whether the data on screen is within budget. We measure the age of what the application actually serves, not just the health of each job.
- **The product has to accept the idea of "as of."** It is the least technical cost and the most real one. Some features cannot live with data that is an hour old. Those have no business on this path.

## When this is the wrong call

If the requirement is measured in seconds, batch reverse ETL is the wrong architecture, and no interval tuning will fix that. Data that must be current to the second belongs to services and events (a topic, a consumer, a continuously maintained projection), not to a warehouse that recomputes every hour.

Before shipping a projection, agree its maximum age and the screen's expired state with the person who uses that number. Those two decisions belong in the acceptance criteria.
