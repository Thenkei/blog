## Context

We already had strong individual uses of Claude Code at RockFi. The problem was no longer proving that an agent could write code. We needed to make good practices available to the whole team and connect AI to the way we actually build products.

We launched **Claude Code Challenges: From Zero to Hero**: asynchronous exercises on real code, each with a deliverable, a review, and—most importantly—a record of what failed. The sequence covered context, implementation from a spec, debugging with falsifiable hypotheses, parallel agents, hooks, and skills.

## The problem

Individual usage is hard to reproduce. The effective prompt stays in a terminal history; an important convention does not appear when needed; a clean document loses the intent of the workshop; an issue slices code without preserving expected value.

Between product discovery and a PR, context crosses several handoffs. Each handoff can lose the original problem, a decision, a boundary, or the definition of done. Accelerating implementation alone moves the bottleneck without improving delivery.

## Bad ideas

- Buy a tool and call it an adoption strategy.
- Measure progress through generated code or content volume.
- Search for one universal prompt across roles and repositories.
- Automate an unstable workflow before clarifying owners and gates.
- Let an agent publish a product decision or merge a PR because tests pass.

Speed creates value only while the output stays connected to verifiable intent.

## What did not work

One-off demos created excitement but few habits. Long guides were rarely reopened at the precise moment a rule mattered. The best workflows remained personal.

We also tried sequences that were too linear: PRD, design, tasks, code. Real work is recursive. A false assumption discovered during implementation must be able to reopen design. Without feedback, automation accelerates a decision that is no longer true.

Large prompts carrying every piece of context also mixed facts, instructions, and old decisions. They were expensive to maintain and hid contradictions.

## Alternatives

We could maintain a prompt library, build a central platform, or let each team choose its own practices. We chose **composable plugins**: small enough to own a precise workflow, versioned with templates and guardrails, and connected through explicit contracts.

The Value Engineering plugin helps facilitate a workshop or distil a conversation into a **DiveIn** document. Delivery capabilities turn a definition of done and slices into reviewable tasks. The engineering plugin governs branches, commits, tests, PRs, and review. Other capabilities cover discovery, QA plans, rollout, and blind-spot analysis.

## The solution

We call the system our **Product OS**. It is not an autonomous agent. It is a human-led loop equipped with reusable workflows:

```text
Problem discovery
        ↓
PRD and expected outcomes
        ↓
Value Engineering workshop
        ↓
DiveIn: decision, boundaries, definition of done
        ↓
Slices and tasks for automated planning
        ↓
Implementation, tests, and PR
        ↓
Human review, release, and learning
        └───────────────────────↺
```

Each step produces an artefact the next one can use. Plugins retrieve context from authorised sources, expose what is missing, and prepare output. Human gates remain on product decisions, architecture choices, sensitive changes, and merge.

The challenges made this possible by surfacing real practices before we encoded them. A shared failure became an edge case; a repeated workflow became a skill; a critical rule became a hook.

The intended result is not “more deliverables”. It is less context reconstructed at each handoff and more attention available for decisions requiring knowledge of the product, customers, and system.

## Limits

A plugin can standardise a bad practice as effectively as a good one. Every workflow therefore needs an owner, evaluation, and an exit path when context is insufficient.

The Product OS replaces neither product strategy, domain expertise, nor technical review. It also creates a surface to maintain: permissions, templates, connectors, tool compatibility, and observability. Not every piece of work should cross the whole chain; a small reversible change deserves a short path.

Final accountability remains human. AI transports and transforms context; it does not own the outcome.
