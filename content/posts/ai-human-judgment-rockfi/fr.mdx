## Le contexte

Nous avions déjà des usages individuels solides de Claude Code chez RockFi. Le problème n'était plus de prouver qu'un agent pouvait écrire du code. Il fallait rendre les bonnes pratiques accessibles à toute l'équipe et connecter l'IA à notre manière réelle de construire un produit.

Nous avons lancé les **Claude Code Challenges: From Zero to Hero** : des exercices asynchrones sur du vrai code, avec un livrable, une review et surtout le partage de ce qui avait échoué. La progression couvrait le contexte, l'implémentation depuis une spec, le debug par hypothèses falsifiables, les agents parallèles, les hooks et les skills.

## Le problème

Un usage individuel reste difficile à reproduire. Le prompt efficace vit dans un historique de terminal ; la convention importante n'arrive pas au bon moment ; le document produit est propre mais perd l'intention du workshop ; une issue découpe le code sans préserver la valeur attendue.

Entre une découverte produit et une PR, le contexte traverse plusieurs handoffs. Chaque handoff peut perdre le problème initial, une décision, une limite ou la définition de « terminé ». Accélérer uniquement l'implémentation déplace le goulot d'étranglement sans améliorer le delivery.

## Les mauvaises idées

- Acheter un outil et appeler cela une stratégie d'adoption.
- Mesurer le progrès au volume de code ou de contenu généré.
- Chercher un prompt universel pour tous les rôles et tous les dépôts.
- Automatiser un workflow instable avant d'en clarifier les owners et les gates.
- Laisser l'agent publier une décision produit ou merger une PR parce que les tests passent.

La vitesse n'a de valeur que si le résultat reste relié à une intention vérifiable.

## Ce qui n'a pas marché

Les démonstrations ponctuelles créaient de l'enthousiasme, mais peu de nouvelles habitudes. Les guides longs étaient rarement relus au moment précis où une règle devenait utile. Les meilleurs workflows restaient ceux de quelques personnes.

Nous avons aussi testé des séquences trop linéaires : PRD, conception, tâches, code. Dans la réalité, une mauvaise hypothèse découverte pendant l'implémentation doit pouvoir rouvrir la conception. Sans boucle de retour, l'automatisation accélère une décision devenue fausse.

Enfin, les gros prompts qui transportaient tout le contexte mélangeaient faits, instructions et anciennes décisions. Ils coûtaient cher à maintenir et masquaient les contradictions.

## Les alternatives

Nous pouvions maintenir une bibliothèque de prompts, construire une plateforme centralisée ou laisser chaque équipe choisir ses pratiques. Nous avons préféré des **plugins composables** : assez petits pour appartenir à un workflow précis, versionnés avec leurs templates et leurs garde-fous, mais reliés par des contrats explicites.

Le plugin de Value Engineering aide à conduire un workshop ou à distiller une conversation dans un document **DiveIn**. Le plugin de delivery transforme ensuite une définition de done et des slices en tâches reviewables. Le plugin engineering encadre branche, commit, tests, PR et review. D'autres capacités couvrent la discovery, le plan QA, le rollout et la recherche d'angles morts.

## La solution

Nous appelons cet ensemble notre **Product OS**. Ce n'est pas un agent autonome. C'est une boucle humaine équipée de workflows réutilisables :

```text
Découverte du problème
        ↓
PRD et résultats attendus
        ↓
Workshop Value Engineering
        ↓
DiveIn : décision, limites, definition of done
        ↓
Slices et tâches pour la planification automatisée
        ↓
Implémentation, tests et PR
        ↓
Review humaine, release et apprentissage
        └───────────────────────↺
```

Chaque étape produit un artefact exploitable par la suivante. Les plugins recherchent le contexte dans les sources autorisées, signalent ce qui manque et préparent une sortie. Des gates humaines restent placées sur les décisions produit, les choix d'architecture, les changements sensibles et le merge.

Les challenges ont rendu cette construction possible : ils ont fait émerger les pratiques réelles avant que nous les encodions. Un échec partagé pouvait devenir un cas limite ; un workflow répété pouvait devenir un skill ; une règle critique pouvait devenir un hook.

Le résultat recherché n'est pas « plus de livrables ». C'est moins de contexte reconstruit à chaque handoff et davantage de temps consacré aux décisions qui exigent une connaissance du produit, des clients et du système.

## Les limites

Un plugin peut standardiser une mauvaise pratique aussi efficacement qu'une bonne. Chaque workflow a donc besoin d'un owner, d'une évaluation et d'une voie de sortie lorsque le contexte ne suffit pas.

Le Product OS ne remplace ni une stratégie produit, ni l'expertise métier, ni la review technique. Il ajoute aussi une surface à maintenir : permissions, templates, connecteurs, compatibilité des outils et observabilité. Enfin, tous les travaux ne doivent pas traverser la chaîne complète ; un petit changement réversible mérite un chemin court.

La responsabilité finale reste humaine. L'IA transporte et transforme le contexte ; elle ne devient pas propriétaire du résultat.
