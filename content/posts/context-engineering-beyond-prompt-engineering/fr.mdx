## Le prompt tient sur un Post-it

Le prompt engineering travaille la formulation d'une instruction. L'ingénierie du contexte choisit ce que l'agent doit voir pour l'interpréter : état du dépôt, décisions produit, conventions, permissions et historique utile.

« Mettre à jour le tunnel de paiement » ne dit pas quelle branche fait foi, quel invariant financier protéger ni si l'agent doit proposer un patch ou le déployer.

Quand l'agent accède à plusieurs systèmes, ce contexte devient une interface : il lui faut une provenance, des droits d'accès, une durée de validité et une règle pour les informations manquantes.

## Une réponse cohérente peut être complètement à côté

Un agent peut prendre une ancienne proposition pour une décision actuelle, ou une permission de lecture pour une autorisation d'agir. Si une information manque, il devine ; si elle est périmée, il répond pour l'ancienne version du système. Trop d'informations peuvent aussi masquer la contrainte essentielle.

Ajouter « sois rigoureux » dans le prompt ne corrige aucun de ces problèmes.

## Le buffet à volonté du contexte

Charger tout le dépôt « au cas où » rend les priorités moins visibles. Dans un fichier d'instructions monolithique, les règles actuelles côtoient les anciennes. Une recherche par similarité peut même retrouver un document périmé et manquer une décision récente formulée autrement.

Les outils comptent aussi. Donner tous les accès dès le départ élargit les conséquences possibles d'une erreur ; une capacité technique n'est pas une autorisation métier.

## Préparer le bon sac pour la bonne mission

Le contexte peut être **fourni** au démarrage, **récupéré** au besoin ou **produit** par une étape précédente. Le premier consomme de la place, le deuxième dépend de la recherche, le troisième peut propager une erreur.

Une revue de PR demande le diff et les conventions de revue ; un incident demande une chronologie, des logs et l'état du déploiement. Le même paquet générique sert mal les deux.

## Le contexte a besoin d'un ordre

Nous organisons le contexte de travail comme une pile :

1. **Autorité** : objectif utilisateur et frontières d'action.
2. **État courant** : branche, diff, schéma ou document réellement en vigueur.
3. **Contrats** : invariants métier, conventions et critères de fin.
4. **Historique pertinent** : décisions et échecs qui expliquent l'état courant.
5. **Preuves** : tests, métriques, logs et sources permettant de vérifier la sortie.

Chaque source indique son responsable, sa provenance, son périmètre et sa durée de validité. Les instructions critiques ont une priorité explicite ; les outils sont accordés quand ils deviennent nécessaires. Si deux sources faisant autorité se contredisent, l'agent doit signaler le conflit.

## Tester le chemin, pas seulement la réponse

Testons aussi le chemin : une règle périmée, deux sources contradictoires ou un document interdit. L'agent doit signaler le problème, pas le transformer discrètement en réponse plausible.

## Parfois, un fichier suffit vraiment

Cette discipline ne corrige ni une source fausse ni un objectif mal défini, et son infrastructure doit être maintenue. Une petite modification réversible peut se contenter d'un prompt et d'un fichier. Le travail supplémentaire se justifie quand le workflow se répète, traverse plusieurs systèmes ou peut déclencher une action à conséquences.
