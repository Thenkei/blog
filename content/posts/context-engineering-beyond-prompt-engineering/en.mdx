## The prompt fits on a Post-it

Prompt engineering works on the wording of an instruction. Context engineering selects what the agent needs to interpret it: repository state, product decisions, conventions, permissions, and relevant history.

“Update the checkout flow” does not say which branch is current, which payment invariant matters, or whether the agent should propose a patch or deploy it.

When an agent has access to several systems, this context has to be specified like an interface: where each piece comes from, who can access it, how long it stays valid, and what to do when information is missing.

## A coherent answer can still be wrong

An agent may treat an old proposal as a current decision, or read access as permission to act. If information is missing, it guesses. If it is stale, it answers for an older version of the system. Too much information can also hide the one constraint that matters.

I have seen two of these at work: an agent treating an outdated proposal as the current decision, and an agent filling in missing information with a plausible guess.

Adding “be rigorous” to the prompt fixes none of these problems.

## Too much context

Loading the whole repository “just in case” makes priorities harder to see. In a monolithic instruction file, current rules sit next to old ones. A similarity search can return an obsolete document and miss a recent decision that is worded differently.

The same goes for tools. Giving the agent every tool from the start makes the consequences of a mistake larger. Having technical access to a system does not mean being authorised to act on it.

## Choose the context for the task

Context can be **provided** at startup, **retrieved** when needed, or **produced** by an earlier step. The first takes up space, the second depends on search quality, and the third can carry errors forward.

A PR review needs the diff and review conventions; an incident needs a timeline, logs, and deployment state. Giving both exactly the same context does not work.

## Context needs an order

We try to organise the working context as a stack. Today this is only partly in place: some layers are explicit, others are still implicit or missing. The target looks like this:

1. **Authority**: user intent and action boundaries.
2. **Current state**: the branch, diff, schema, or document actually in force.
3. **Contracts**: domain invariants, conventions, and completion criteria.
4. **Relevant history**: decisions and failures that explain the current state.
5. **Evidence**: tests, metrics, logs, and sources used to verify the output.

Each source records its owner, provenance, scope, and validity period. Critical instructions have an explicit priority; access to a tool is granted when it becomes necessary. If two authoritative sources contradict each other, the agent should report the conflict.

## Test with bad context too

The agent should also be tested with bad context: a stale rule, two sources that contradict each other, or a document it is not allowed to use. It should report the problem. It should not quietly turn it into a plausible answer.

## Sometimes one file is enough

This discipline does not fix a wrong source or a badly defined goal, and its infrastructure has to be maintained. For a small, reversible change, a prompt and a file can be enough. The extra work is justified when the workflow repeats, spans several systems, or can trigger an action with serious consequences.
