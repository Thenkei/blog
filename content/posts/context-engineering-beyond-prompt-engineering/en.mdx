## Context

Prompt engineering optimises an instruction. Context engineering designs everything that lets an agent interpret that instruction: repository state, product decisions, team conventions, permissions, relevant history, and runtime signals.

As agents gain access to code, Notion, GitHub, and internal data, context becomes an interface between systems. It deserves API-level discipline: a contract, provenance, access control, freshness, and defined behaviour when data is absent.

## The problem

An agent does not naturally distinguish a current decision from an old proposal, a fact from an assumption, or read access from authority to act. It produces the most coherent answer from what it receives.

Missing context forces a guess. Stale context produces an answer for the previous system. Excess context buries important constraints. Broad context also increases the blast radius of an error or hostile instruction.

## Bad ideas

- Add “be rigorous” to a prompt backed by incomplete sources.
- Load the entire repository and history “just in case”.
- Hide critical instructions in a long document without explicit priority.
- Confuse technical capability with domain authorisation.
- Evaluate only the final answer without checking which sources produced it.

More context is not necessarily better context. It is a larger interpretation surface.

## What did not work

Monolithic instruction files quickly accumulated contradictory and stale rules. Agents applied them inconsistently depending on ordering and task.

Similarity-only retrieval sometimes selected a lexically close but obsolete document while missing a recent decision written in different language.

Giving an agent every tool from the start made demos easier but audits harder: we could no longer tell which access the workflow actually required.

## Alternatives

Context can be **pushed** at startup, **retrieved** on demand, or **produced** by a previous step. Each has a cost: push guarantees a baseline but consumes budget; retrieval reduces volume but depends on search quality; production preserves continuity but can propagate an error.

The right combination depends on the task. A PR review needs the current diff and review conventions. An incident investigation needs a timeline, logs, and deployment state. One generic bundle serves both badly.

## The solution

We treat context as an ordered stack:

1. **Authority**: user intent and action boundaries.
2. **Current state**: the branch, diff, schema, or document actually in force.
3. **Contracts**: domain invariants, conventions, and completion criteria.
4. **Relevant history**: decisions and failures that explain current state.
5. **Evidence**: tests, metrics, logs, and sources used to verify output.

Each source carries ownership or provenance, a validity period, and a scope. Tools are granted with least privilege when needed. If a critical source is missing or contradictory, the agent stops and exposes the ambiguity.

Evaluation also tests perturbations: what happens with a stale rule, two conflicting sources, or an unauthorised document? A good answer obtained from the wrong context remains a fragile system.

## Limits

Context engineering cannot repair a bad objective, a false source, or a model that cannot reason about the domain. It also adds a platform to maintain: indexing, permissions, invalidation, and observability.

Formalising everything would be a mistake. A short task may need only a prompt and one file. The discipline pays off when a workflow repeats, crosses systems, or can trigger a material action.
