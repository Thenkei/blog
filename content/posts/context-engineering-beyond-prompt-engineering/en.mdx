## The prompt fits on a Post-it

Prompt engineering asks how an instruction should be phrased. Context engineering asks what the agent must be able to see in order to interpret that instruction: the current repository state, product decisions, team conventions, permissions, relevant history, and runtime signals.

The prompt may say “update the checkout flow”. The work still depends on which branch is current, which product decision won, which payment invariant must not change, and whether “update” means propose a patch or deploy it. The clever sentence is only a small part of the brief.

As agents gain access to code, Notion, GitHub, and internal data, context becomes an interface between systems. It deserves the discipline we expect from an API: a contract, provenance, access control, freshness, and defined behaviour when something is absent.

## Coherent is not the same as correct

An agent does not naturally distinguish a current decision from an old proposal, a fact from an assumption, or read access from authority to act. It produces the most coherent answer it can from what it receives.

That creates several distinct failure modes. Missing context forces a guess. Stale context produces a good answer for the previous version of the system. Excess context buries the constraint that mattered. Context that is too broad increases the blast radius of both ordinary mistakes and hostile instructions.

Adding “be rigorous” to the prompt fixes none of them.

## The all-you-can-eat context buffet

Loading the entire repository and its history “just in case” feels safe because nothing has been deliberately omitted. In practice, it creates a larger interpretation surface and makes priority harder to see.

Monolithic instruction files develop the same problem over time. Current rules sit beside stale ones, contradictions accumulate, and the agent's behaviour changes with ordering and task. Similarity-only retrieval can then make a precise-looking mistake: it selects an obsolete document because the wording is close while missing a recent decision written in different language.

Tool access belongs in this discussion too. Giving every tool to an agent from the first step makes a demo smooth and an audit murky. Technical capability is not domain authorisation, and unused access is still part of the blast radius.

More context is not automatically better context. Sometimes it is simply more material to misunderstand.

## Pack for the task in front of you

Context can arrive in three ways. It can be **pushed** at startup, **retrieved** when a need appears, or **produced** by a previous step. None is free: push guarantees a baseline but spends the context budget; retrieval keeps the bundle smaller but depends on search quality; produced context preserves continuity but can also carry an earlier error forward.

The useful combination follows the task. A PR review needs the current diff and the team's review conventions. An incident investigation needs a timeline, logs, and deployment state. Giving both workflows the same generic bundle means arriving at code review with all the production logs, then bringing the style guide to an outage: nothing is technically wrong, but the essentials are elsewhere.

## Context needs an order

We organise the working context as a stack:

1. **Authority**: user intent and action boundaries.
2. **Current state**: the branch, diff, schema, or document actually in force.
3. **Contracts**: domain invariants, conventions, and completion criteria.
4. **Relevant history**: decisions and failures that explain the current state.
5. **Evidence**: tests, metrics, logs, and sources used to verify the output.

Each source records its owner and provenance, its validity period, and its scope. Critical instructions have an explicit priority instead of relying on where they happen to appear. Tools are granted with least privilege when they become necessary. If an essential source is missing or two authoritative sources disagree, the agent stops and makes that ambiguity visible.

## Test the route, not just the arrival

Evaluating only the final answer misses half the system. We also need to know which sources produced it and what happens when the route is disturbed.

Give the workflow a stale rule. Present two conflicting sources. Add a document the agent is not authorised to use. A robust system should surface the problem rather than quietly turn it into prose. A good answer obtained from the wrong context is still a fragile system.

## Sometimes one file is enough

Context engineering cannot repair a bad objective, a false source, or a model that cannot reason about the domain. It also creates infrastructure to maintain: indexing, permissions, invalidation, and observability.

Formalising every tiny task would be its own failure mode. A short, reversible change may genuinely need only a prompt and one file. The discipline starts paying for itself when a workflow repeats, crosses systems, or can trigger a material action.
