## The prompt fits on a Post-it

Prompt engineering works on the wording of an instruction. Context engineering selects what the agent needs to interpret it: repository state, product decisions, conventions, permissions, and relevant history.

“Update the checkout flow” does not say which branch is current, which payment invariant matters, or whether the agent should propose a patch or deploy it.

When an agent reaches across systems, context becomes an interface. It needs provenance, access rules, a validity period, and a rule for missing information.

## Coherent is not the same as correct

An agent may treat an old proposal as a current decision, or read access as permission to act. Missing information invites a guess; stale information produces an answer for an older system. Too much information can bury the constraint that matters.

Adding “be rigorous” to the prompt fixes none of them.

## The all-you-can-eat context buffet

Loading the whole repository “just in case” makes priorities harder to see. In a monolithic instruction file, current rules sit beside stale ones. Similarity search may even retrieve an obsolete document while missing a recent decision phrased differently.

Tools matter too. Granting every capability at the start increases the potential impact of an error; technical access is not domain authorisation.

## Pack for the task in front of you

Context can be **provided** at startup, **retrieved** when needed, or **produced** by an earlier step. The first takes up space, the second depends on search quality, and the third can carry errors forward.

A PR review needs the diff and review conventions; an incident needs a timeline, logs, and deployment state. The same generic bundle serves neither particularly well.

## Context needs an order

We organise the working context as a stack:

1. **Authority**: user intent and action boundaries.
2. **Current state**: the branch, diff, schema, or document actually in force.
3. **Contracts**: domain invariants, conventions, and completion criteria.
4. **Relevant history**: decisions and failures that explain the current state.
5. **Evidence**: tests, metrics, logs, and sources used to verify the output.

Each source records its owner, provenance, scope, and validity period. Critical instructions have an explicit priority; tools are granted when needed. If two authoritative sources disagree, the agent should surface the conflict.

## Test the route, not just the arrival

Test the route too: a stale rule, conflicting sources, or a document the agent cannot use. It should flag the problem rather than quietly turn it into a plausible answer.

## Sometimes one file is enough

This discipline cannot repair a false source or a poorly defined goal, and its infrastructure needs maintenance. A small, reversible change may need only a prompt and a file. The extra work pays off when a workflow repeats, crosses systems, or can trigger a consequential action.
