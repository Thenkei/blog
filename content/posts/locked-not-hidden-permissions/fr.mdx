Dans le back office de RockFi, l'interface cache ce que les permissions d'un utilisateur refusent. Sans la permission de modifier une section, les boutons d'écriture ne sont pas rendus. Sans la permission d'en lire une autre, l'onglet ou la carte qui l'affiche disparaît.

L'utilisateur voit une page avec des morceaux en moins et aucune explication. Il ne peut pas distinguer une permission manquante d'une fonctionnalité qui n'est pas déployée. Il ne sait pas non plus à qui s'adresser.

Le déclencheur : je cherchais une section que je ne trouvais pas. Le problème venait finalement d'ailleurs, mais c'est ce qui m'a décidé à ouvrir cette pull request.

J'ai ouvert une pull request qui change cette règle : ce que les permissions refusent reste affiché, verrouillé, avec le nom des groupes qui détiennent la permission.

Je parle ici du back office que RockFi utilise aujourd'hui. Nexus, que décrit la série [Outils internes à la pointe](../posts/internal-tools-are-a-product), était une proposition, et [une autre solution a été retenue](../posts/internal-tools-still-believe). Les noms de permissions et de groupes de cet article sont inventés, et le code est simplifié.

## La règle actuelle

La règle du projet a deux parties. Un contrôle d'écriture n'est rendu que si l'utilisateur a la permission d'écrire. Ce que la page liste sans que l'utilisateur puisse l'ouvrir, un document ou une entrée du menu latéral, reste visible, désactivé, avec un cadenas et la raison. Le guide d'interface du projet le justifie ainsi : caché, l'élément aurait l'air manquant ou cassé.

La pull request étend la deuxième partie aux contrôles d'écriture et aux sections.

## Trois composants

**L'action verrouillée.** Un bouton d'écriture (enregistrer, créer, ajouter) reste à sa place, désactivé. Au survol, il affiche la raison : « Réservé au groupe Opérations : demandez l'accès à un administrateur. »

**La notice de lecture seule.** La page écrit la même raison une fois, en texte, sous son en-tête : « Lecture seule. Les modifications sont réservées au groupe Opérations. » Une carte qui dépend d'une autre permission a sa propre notice. Sur une page de liste, la raison tient en une ligne sous les actions de l'en-tête.

**La section à accès restreint.** Un onglet ou une carte que l'utilisateur n'a pas le droit de lire garde sa place et son titre. Son contenu est remplacé par un bloc « Accès restreint » qui nomme les groupes.

Ces trois composants sont dans un seul fichier, pour que le verrouillage ait la même forme sur toutes les pages. C'est l'argument des primitives dans [La cohérence par défaut, pas par convention](../posts/internal-tools-consistency-by-default).

## Comment le bouton est désactivé

```tsx
// Exemple simplifié. Les noms sont inventés pour l'article.
function LockedAction({ permission, children }: LockedActionProps) {
  const { allows, reasonFor } = usePermissions();

  if (allows(permission)) return <>{children}</>;

  return (
    <span title={reasonFor(permission)}>
      <fieldset disabled style={{ display: "contents" }}>
        {children}
      </fieldset>
    </span>
  );
}

<LockedAction permission="orders.edit">
  <Button onClick={save}>Enregistrer</Button>
</LockedAction>
```

Le composant entoure ses enfants d'un `fieldset disabled`. Le navigateur désactive alors tous les contrôles de formulaire qu'il contient. Il n'y a pas besoin de cloner les enfants pour leur passer une prop `disabled`, et chaque bouton garde ses propres props.

Un bouton désactivé ne reçoit pas les événements de la souris, donc un `title` posé sur lui ne s'afficherait jamais. C'est le `span` autour qui le porte.

Un `fieldset` ne désactive pas les liens. Quand l'action est un lien vers une page de création, c'est la page qui rend un bouton à la place pour les utilisateurs sans la permission. Le composant ne le fait pas pour elle.

## Au clavier et avec un lecteur d'écran

Le `title` ne s'affiche qu'au survol. Au clavier, un bouton désactivé sort de l'ordre de tabulation et le `span` ne prend pas le focus. Sur un écran tactile, il n'y a pas de survol. La notice existe pour ces utilisateurs : la raison est dans la page, en texte.

La notice n'est pas reliée aux boutons. À la lecture du code, un lecteur d'écran qui arrive sur un bouton verrouillé l'annonce comme indisponible, sans la raison : le `title` est sur un autre élément, et aucun `aria-describedby` ne pointe vers la notice. Sur une page de liste, la ligne sous les actions a un identifiant que le bouton ne référence pas. L'utilisateur doit avoir lu la raison ailleurs dans la page. La pull request ne règle pas ce point.

Je n'ai testé ni au clavier ni avec un lecteur d'écran.

Le guide de pratiques ARIA du W3C décrit deux conventions pour un contrôle désactivé : le retirer de l'ordre de tabulation avec `disabled` quand les contrôles voisins suffisent à deviner qu'il existe, ou le garder focalisable avec `aria-disabled` quand il doit rester découvrable. Les boutons verrouillés suivent la première. Dans les menus, une entrée verrouillée porte `aria-disabled` et un cadenas à la place de son icône.

## Ce qui reste caché

Les actions de chaque ligne d'un tableau (modifier, supprimer, annuler) restent cachées pour ceux qui ne les ont pas. Un cadenas sur chaque ligne serait du bruit, et la notice de la carte dit déjà pourquoi.

La page d'accueil ne montre que les sections de l'utilisateur. C'est un résumé de son propre travail.

Une action que l'état de l'objet n'autorise pas reste absente pour tout le monde : personne ne se voit proposer la suppression d'une commande déjà validée. Le statut décide quelles actions existent. Les groupes de l'utilisateur ne font que les verrouiller.

La nouvelle règle est écrite dans le guide de contribution et dans la checklist que suivent les agents de code : rien n'est caché faute de permission, et les actions de ligne sont les seuls contrôles cachés.

## Le serveur refuse toujours

Le verrouillage est de l'affichage. Chaque fonction serveur commence par vérifier la permission, et un appel refusé est journalisé avec l'utilisateur et les permissions qu'il demandait. Un bouton désactivé n'ajoute aucune protection, et le cacher n'en ajoutait pas non plus. C'est le principe que je décrivais pour Nexus dans [Une gouvernance qu'on ne peut pas oublier](../posts/internal-tools-governance-by-construction) : le contrôle d'accès est côté serveur, que l'écran y pense ou non.

La section à accès restreint ajoute une précaution. Tant que les permissions ne sont pas connues, elle ne rend rien, donc son contenu ne lance aucune requête. Sinon la page demanderait des données que le serveur va refuser. Un test vérifie que l'appel n'est pas émis pour un utilisateur sans la permission de lecture.

Dans les tests existants, les assertions « le bouton est absent » deviennent « le bouton est désactivé et la notice est visible ».

## Ce que le verrouillage révèle

Afficher verrouillé apprend à chaque utilisateur qu'une fonctionnalité existe et quels groupes la détiennent. Pour les champs, j'avais défendu le même choix dans l'article sur la gouvernance : masquer la valeur plutôt que retirer la colonne.

Une recommandation publique connue va dans l'autre sens pour les permissions. Dans « Hidden vs. Disabled In UX » (Smashing Magazine, 2024), Vitaly Friedman pose une question : cet utilisateur pourra-t-il un jour interagir avec l'élément ? Si la réponse est non, par exemple à cause des permissions, il conseille de cacher. Il conseille de désactiver quand on veut que l'utilisateur sache qu'une fonctionnalité existe sans être disponible, et d'expliquer pourquoi.

Dans notre back office, l'appartenance à un groupe se change dans les réglages, et le message affiché dit de demander l'accès à un administrateur. La réponse à sa question n'est donc pas « jamais ».

La proposition ne prévoit aucune fonctionnalité dont l'existence devrait rester cachée. S'il en arrive une, il faudra l'écrire comme une exception de plus.
