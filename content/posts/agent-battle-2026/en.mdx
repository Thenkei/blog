In a few months, we moved from an editor assistant to agents that can explore a repository, edit files, run tests, and prepare a PR. We use **Claude Code** and **Codex**, among others, and we are experimenting with **Herd** to operate several native agents from one interface.

The obvious question, “which one is best?”, got us nowhere. A benchmark or an isolated demo says almost nothing about the ticket waiting for us this morning. And imposing one tool on every workflow in the team would have closed the debate without answering it. What matters is the type of task: an interactive investigation, a well-specified task we can delegate, or several independent units to coordinate.

## What an agent costs us

An agent writes code quickly. The cost comes afterwards: preparing the context, watching the session, resolving conflicts, and reviewing. We tried it, with more than five agents on a design that was still uncertain. We got as many interpretations to reconcile, and diffs nobody could integrate.

That is also why we stopped counting gains in lines of code. What we measure is the time it takes to get a reliable, reviewed change.

Choosing a tool also decides where the code runs, which secrets are available, how an action is approved, where the logs are kept, and who can stop a task. An exploration agent and a delivery agent do not need the same permissions. Giving them the same ones is a shortcut we only notice afterwards.

## What we got wrong first

At first, we kept switching from one tool to another. We lost context each time: every transfer needed a new summary and brought assumptions back in.

We also parallelised tasks that were coupled. We got file collisions and incompatible decisions. Two tasks that can run in parallel on a board are not necessarily independent in the repository. An orchestrator makes these collisions visible, which helps, but it does not make them go away.

Long tasks without checkpoints produced impressive diffs that were painful to review. The agent had met its end condition, but nothing required it to produce a change we could understand. With more sessions than the team can seriously review, we end up skimming.

## Choose the mode before the tool

We now distinguish three modes:

| Mode | Good fit | Primary control |
| --- | --- | --- |
| Interactive pairing | Ambiguous problem, exploration, debugging | Frequent human direction |
| Bounded delegation | Clear issue, testable criteria, isolated diff | Sandbox, budget, completion evidence |
| Orchestration | Genuinely independent tasks | Worktree isolation and explicit integration |

Claude Code and Codex can each cover several modes, depending on their environment. Herd adds a supervision layer for several agents. It becomes useful once the work is properly split and one person has several flows to follow. While we are still discovering the problem, it mostly adds windows to watch.

## How we choose now

We choose the mode based on risk and uncertainty:

1. **Understand before parallelising.** One person and one agent explore until boundaries are clear.
2. **Define a task contract.** Scope, authorised files or systems, completion criteria, expected tests, and stop condition.
3. **Delegate the smallest useful task whose result we can review.**
4. **Parallelise only independent units.** Each agent works in an isolated environment.
5. **Integrate under human accountability.** Review covers invariants as well as the diff and tests.

We compare five things: the time before a first result we can check, how the tool handles context, how well we can control its actions, the review effort, and the attention needed to follow the agents. The best tool is the one that asks the least effort from us to get a reliable result. An agent that writes fast but needs two hours of review does not save us much.

## Limits of this framework

This framework depends on our organisation, our repositories, and our security constraints. Products change quickly, and a model or interface advantage can disappear within a few weeks. So we reassess on real workflows rather than defend an old ranking. That is also why I do not name a winner here. The tool I reach for first keeps changing, every few weeks, with the releases.

Multi-agent orchestration also adds a distributed system to engineering work: queues, partial states, conflicts, and recovery. For a short or tightly coupled task, it often increases the total time. For those tasks, I prefer to stay with a single agent.
