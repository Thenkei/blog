_Note: This article was written post-mortem, after my departure from Forest Admin._

Storing complex and large objects in Redis for sub-millisecond serving is a great idea, as long as they fit in RAM. At Forest Admin, we learned the hard way that a single Redis instance trusted with everything can also take everything down at once.

Here is the story of a weekend outage caused by an Out-Of-Memory (OOM) error, and what it taught us about architecture and data lifecycles.

## The Context

<ArticleDiagram visualId="redis-memory-exhaustion-post-mortem" />

To achieve sub-millisecond latency for some heavily accessed data, we built a use case that cached complex, large objects in Redis.

This feature was implemented 2 to 3 years before the incident. At the time, we had fewer clients, and the objects being stored were tiny anyway. In fact, most of the engineering team dealing with the incident (myself included) wasn't even at the company when this code was originally written.

Because Redis is fast and reliable, it had gradually become our default answer to a bunch of other needs:

- **BullMQ**: Queueing and executing background jobs.
- **Authentication**: Managing user sessions.
- **Security**: Anti-brute force mechanisms and rate limiting.

All of these distinct processes were happily co-existing inside a **single Redis instance**.

## A Memory Graph Nobody Was Watching

As Forest Admin grew, so did our clients' use cases. What started as small, innocuous cached objects slowly expanded into massive data structures. Since the growth was gradual, no single day looked abnormal: the memory graph just climbed a few pixels a week.

Then, it happened on a weekend. A sudden spike in data volume did the rest. Before anyone noticed, our Redis instance hit its memory limit.

The consequences were immediate and widespread. Because everything relied on that single instance, the issue wasn't isolated to just the caching layer:

- **Job Queues Stopped**: BullMQ couldn't write or read jobs, bringing background processing to a halt.
- **Authentication Broke**: Users couldn't log in or maintain their sessions.
- **Security Mechanisms Failed**: Our anti-brute force tracking went offline.

The whole platform was degraded, because of a cache that was never supposed to be critical.

## The Root Causes

When we investigated the incident, several failures in our infrastructure design and data lifecycle management stood out:

### 1. No Memory Alarms in Datadog

While we had monitoring in place, we hadn't set up specific alerts for Redis memory consumption. The instance silently ballooned until it crashed, giving us no preemptive warning to scale up or intervene before the limit was reached.

### 2. The Single Point of Failure (SPOF) Architecture

By coupling highly volatile, memory-intensive caching with mission-critical system infrastructure (like authentication and job queues) on the exact same instance, we created a massive single point of failure. A memory exhaustion issue in one domain entirely took down completely unrelated domains.

### 3. Inefficient Data Lifecycles

We initially thought we had data retention covered. We had a TTL (Time-To-Live) configured, but it simply wasn't aggressive enough. Worse, we weren't actively purging data belonging to deleted projects: stale objects were holding RAM on behalf of projects that no longer existed.

## The Fixes & Takeaways

First, we split the architecture: caching, queues, and sessions now live in isolated Redis instances. That left the underlying problem, the data itself. We:

- **Shortened the TTLs**: Making them much more aggressive to ensure memory is freed up faster.
- **Cleaned up Stale Data**: Implementing routines to immediately remove cached items belonging to deleted projects.
- **Compressed the Payloads**: A colleague ([Guillaume Gautreau](https://www.ghusse.com/redis/node/compress/does-it-worth-compressing-large-json-in-redis/)) took the time to study and implement a compression solution for the data _before_ it gets stored in Redis. It cut our memory usage significantly and, since smaller payloads travel faster, shortened HTTPS transport times too.

<MotionScene id="redis-cache-lifecycle-fixes" />

If you run Redis in production, the lesson fits in one question: what happens to your sessions and jobs the day your cache fills up the RAM? For us, the answer was "they go down with it." And a caching strategy tuned for a handful of clients doesn't retune itself when their data grows.
