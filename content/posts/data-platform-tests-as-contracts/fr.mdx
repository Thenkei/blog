Troisième épisode de **Ce que coûte une donnée fiable**. Le précédent se terminait sur une promesse : qu'une donnée fausse s'arrête dans le pipeline, pas dans un rendez-vous client.

Nous avons détecté et qualifié de nombreuses erreurs dans les données envoyées par les providers. Je ne peux pas détailler ces incidents. Je peux expliquer le problème qu'ils nous laissent : distinguer une ligne mal formée, un flux incomplet et un chiffre dont la structure est correcte mais le sens est faux.

## Arrêter le run avant la publication

Un job de qualité exécuté après la publication peut détecter un incident, mais pas empêcher le premier lecteur de voir le mauvais résultat. Les contrôles du chemin de publication doivent tourner avant que ce résultat quitte la plateforme.

Sur un chemin de publication protégé, un check bloquant en échec doit empêcher l'aval de partir. L'application peut conserver la dernière version validée seulement tant qu'elle reste dans son budget de fraîcheur. Ensuite, le chiffre doit devenir indisponible, comme décrit dans l'épisode 2.

> Un dernier chiffre validé reste utile tant que son âge est acceptable. « Dernier état correct » ne veut pas dire « garanti à vie ».

## Où placer les tests (aux frontières, pas partout)

Sur des millions de lignes, un test peut être une requête coûteuse. On place les contrôles là où ils répondent à une question précise, puis on décide si un échec impose un arrêt de publication ou une investigation.

**À l'entrée : la source nous envoie-t-elle encore des données ?** Fraîcheur, et les clés qui doivent exister. dbt sait mesurer la fraîcheur d'une source à partir d'une colonne de chargement :

```yaml
# models/sources.yml (exemple simplifié)
sources:
  - name: partner_feed
    schema: raw_partner_feed
    config:
      loaded_at_field: _airbyte_extracted_at
      freshness:
        warn_after: {count: 6, period: hour}
        # Seuils illustratifs ; tenir compte du calendrier de la source.
        error_after: {count: 24, period: hour}
    tables:
      - name: contracts
```

Cette syntaxe correspond à dbt Core 1.10+. `dbt source freshness` se lance séparément de `dbt build`, et son échec doit être relié au chemin de publication. `_airbyte_extracted_at` mesure la présence de lignes récemment extraites, pas l'âge des faits métier. Une source inchangée peut sembler ancienne ; une extraction fraîche peut contenir de vieilles valorisations. Il faut une métadonnée de couverture propre à la source pour distinguer les deux.

**Au milieu : la forme est-elle respectée ?** La couche Silver porte des **contrats** : colonnes, types, contraintes. Un contrat appliqué fait échouer la construction du modèle si le SQL produit autre chose que ce qui est déclaré. C'est là que la dérive de schéma de l'[épisode 1](../posts/data-platform-ingestion-drift) casse bruyamment :

```yaml
# models/silver/_silver.yml
models:
  - name: stg_partner_contracts
    config:
      contract:
        enforced: true
    columns:
      - name: contract_id
        data_type: varchar
        constraints:
          - type: not_null
        data_tests:
          - unique
      - name: amount
        # Si la source envoie "1 234,56", le cast échoue ici, pas dans un tableau de bord.
        data_type: number(18, 2)
      - name: status
        data_type: varchar
        data_tests:
          - accepted_values:
              arguments:
                values: ['active', 'suspended', 'closed']
```

Sur les tables Snowflake standard, `NOT NULL` est appliqué ; les clés primaires et l'unicité déclarées ne le sont pas. On garde donc le test `unique`. Un contrat de type n'insère pas non plus de cast dans le SQL : le modèle fait la conversion, et une erreur de conversion ne doit pas devenir un NULL silencieux sans contrôle.

**À la sortie : le chiffre est-il cohérent avec les données de référence ?** Les tests de forme ne suffisent plus en Gold. On y vérifie des invariants métier, et surtout des **réconciliations** : un total calculé chez nous doit correspondre, à une tolérance près, au total déclaré par la source. Un test singulier dbt est une requête qui doit renvoyer zéro ligne :

```sql
-- tests/assert_totals_reconcile_with_source.sql
-- Chaque ligne renvoyée est un écart que quelqu'un devra expliquer.
select
    entity_id,
    computed_total,
    reported_total,
    abs(computed_total - reported_total) as gap
from {{ ref('gold_entity_totals') }}
where computed_total is null
   or reported_total is null
   or abs(computed_total - reported_total) > greatest(0.01, 0.005 * abs(reported_total))
```

La tolérance est illustrative : les deux montants doivent couvrir les mêmes entités, la même devise et la même date de valorisation. Un pourcentage seul rate les écarts face à zéro, et les comparaisons SQL avec NULL ratent silencieusement les valeurs absentes. La jointure avec la source doit conserver les entités manquantes, sinon elles n'atteignent jamais ce test.

## `dbt build`, pas `dbt run`

`dbt run` construit les modèles ; un `dbt test` séparé les vérifie ensuite. **`dbt build` ordonne les modèles et tests sélectionnés dans le DAG**, et saute les nœuds aval concernés quand un test en erreur échoue. La sélection compte : un test exclu par un sélecteur ne bloque rien. Notre projet utilise `indirect_selection: buildable` pour les tests à plusieurs parents ; le périmètre testé se relit avec le SQL.

Dans Dagster, l'intégration dbt expose chaque modèle comme un asset, et les tests dbt comme des **asset checks** attachés à ces assets :

```python
from dagster import AssetExecutionContext
from dagster_dbt import DbtCliResource, dbt_assets

@dbt_assets(manifest=DBT_MANIFEST_PATH)
def warehouse_models(context: AssetExecutionContext, dbt: DbtCliResource):
    # `build` et pas `run` : les tests tournent entre les modèles, pas après la bataille.
    yield from dbt.cli(["build"], context=context).stream()
```

Le résultat se voit directement dans le graphe d'assets : chaque modèle affiche ses checks, verts ou rouges, à côté de sa dernière matérialisation. Quand quelqu'un demande « pourquoi ce chiffre n'a pas bougé depuis ce matin ? », la réponse est sur la même page que la question.

## Les contrôles de volume dans Dagster

Un contrôle de volume sert à repérer les flux incomplets : chaque ligne reçue peut être valide alors que beaucoup de lignes attendues manquent. SQL sait aussi calculer ça ; Python sert ici à exprimer le verdict comme un asset check Dagster. Le seuil de 10 % ci-dessous est un exemple, pas un SLA commun à toute la plateforme.

```python
from dagster import AssetCheckResult, AssetCheckSeverity, AssetKey, asset_check
from dagster_snowflake import SnowflakeResource

@asset_check(
    asset=AssetKey(["gold", "gold_entity_totals"]),
    # Bloquant : si le check échoue en ERROR, l'aval (reverse ETL compris) ne part pas.
    blocking=True,
    description="Le nombre d'entités ne chute pas de plus de 10 % en une heure.",
)
def entity_volume_did_not_collapse(snowflake: SnowflakeResource) -> AssetCheckResult:
    with snowflake.get_connection() as conn:
        current, previous = conn.cursor().execute(
            """
            select
                count(*),
                (select count(*) from gold.gold_entity_totals at(offset => -3600))
            from gold.gold_entity_totals
            """
        ).fetchone()

    if previous == 0:
        return AssetCheckResult(
            passed=False,
            severity=AssetCheckSeverity.ERROR,
            metadata={"reason": "empty_baseline", "current": current},
        )
    ratio = current / previous
    return AssetCheckResult(
        passed=ratio >= 0.9,
        severity=AssetCheckSeverity.ERROR,
        metadata={"current": current, "previous": previous, "ratio": round(ratio, 3)},
    )
```

Une référence vide bloque dans cet exemple ; son initialisation demande une décision explicite. Un nouveau flux ou un flux saisonnier peut nécessiter une autre fenêtre de comparaison.

Le `at(offset => -3600)` demande que le même objet table ait existé une heure plus tôt, avec une rétention Time Travel suffisante. Un modèle incrémental sans remplacement dans cet intervalle permet de respecter cette condition. Un full refresh, un remplacement ou une nouvelle table peuvent la casser. Dans ces cas, on compare des volumes conservés pour les runs validés, plutôt que de dépendre de cet historique.

`blocking=True` empêche la matérialisation aval sur un échec en ERROR quand le check fait partie du run. Il n'annule pas une table déjà matérialisée et ne protège pas un consommateur qui contourne le graphe. Des runs réactifs séparés demandent aussi la condition sur les checks amont montrée dans l'épisode 2. Il faut enregistrer le check dans `Definitions` et tester le vrai chemin de publication.

## Warn ou error : la vraie décision

Écrire un test est facile. Choisir sa sévérité est la décision qui détermine si le système reste utilisable dans six mois.

- **Trop d'`error`**, et le pipeline s'arrête pour des broutilles. L'équipe apprend à relancer sans lire. Le jour où l'erreur est grave, l'équipe risque de relancer le run sans la lire non plus.
- **Trop de `warn`**, et personne ne lit les avertissements. Un warning que personne ne traite est un test désactivé avec des étapes en plus.

Les warnings se déclenchent souvent sur notre plateforme, parfois parce qu'un nouveau cas provider n'est pas encore pris en compte. Ce n'est pas automatiquement une raison de supprimer le test. Il faut d'abord distinguer une erreur du flux d'un cas valide que notre modèle ne représente pas. Pour une erreur qui bloque la publication, je veux un propriétaire nommé et une action concrète. Les warnings ont aussi besoin d'un circuit de qualification, sans traiter chaque alerte comme une panne de production.

## Quand la forme est correcte et le sens est faux

Les tests vérifient les cas que nous avons anticipés. Un changement de sens dans la source peut leur échapper, même si la structure reste identique.

Une source pourrait, par exemple, continuer d'envoyer une colonne `amount` avec les mêmes types et volumes, mais passer du brut au net de frais. C'est un exemple hypothétique, pas un incident provider que je dévoile. Les tests de forme passeraient encore.

Deux moyens utiles de détecter ce changement :

1. **La réconciliation avec une source indépendante**, quand elle existe. C'est pour ça que le test le moins élégant est le plus précieux.
2. **Un propriétaire métier par modèle Gold**, qui regarde les chiffres et sait quand ils ont « une drôle de tête ». Les outils aident à détecter les écarts. Il faut toujours quelqu'un qui connaît les données pour les interpréter.

## Ce que ça coûte

- **Les tests consomment du calcul.** Restreindre un test d'unicité aux lignes récentes réduit les scans, mais peut rater un doublon avec l'historique. On compare les clés modifiées à l'historique concerné, et on garde un contrôle complet à une fréquence justifiée par le risque.
- **Les calendriers de publication comptent.** Un flux quotidien et un flux limité aux jours ouvrés n'ont pas les mêmes règles. Une alerte répétée le lundi mérite une correction du calendrier, pas un créneau récurrent dans l'astreinte.
- **Un check bloquant est une dépendance de disponibilité.** Si le check lui-même plante (timeout, droit manquant), il bloque l'aval comme un vrai échec. Les checks bloquants doivent être aussi simples et aussi fiables que ce qu'ils protègent.

## Quand c'est le mauvais choix

Si vos données alimentent une analyse exploratoire que personne ne réutilise, des checks bloquants et des propriétaires nommés sont excessifs. Des tests en `warn` et un peu de bon sens suffiront.

Pour vérifier un chemin bloquant, faites échouer volontairement un test dans un run de développement et contrôlez que la publication ne part pas. Puis vérifiez l'écran après expiration du budget de fraîcheur. Un check rouge dans l'interface ne prouve, à lui seul, aucun des deux comportements.
